# Склад App

## Где работать

- Репозиторий [Leonidtt/warehouse-app](https://github.com/Leonidtt/warehouse-app), рабочая ветка `main`. Перед изменениями сверь SHA ветки на GitHub с локальным checkout. Если локальная копия отстаёт или содержит незавершённые правки, работай в отдельном checkout от актуальной версии и сохрани локальные правки.
- Основа — рабочий склад. Её точки входа `backend/main.py` и `backend/index.html`. Обычные изменения интерфейса и складских функций пользователь просил выпускать на Основу. Для задач, явно относящихся к Бете, используй `backend/main_beta.py` и `backend/beta.html`.
- Основа и Бета используют разные SQLite-базы и токены Telegram. На Railway база Основы находится в `/data/warehouse.db`, база Беты — в `/data/warehouse_beta.db`. PWA и Telegram Mini App Основы работают с одной базой. Перенос данных между средами — отдельная операция.
- Фронтенд Основы состоит из `index.html` и подключённых файлов `warehouse_v18.*` и `release_v18*.*`. Ищи также обёртки функций и код, перемещающий элементы после загрузки страницы. Настройки собираются в `warehouse_v18.js`. Сводка «На руках» формируется в `release_v184.js` и `release_v184.py`.

## Правила вспышек и архива выкупа (21.11.2026)

- Отдельная вспышка — оборудование категории «Вспышки». Её отображаемое название — только порядковый номер: «1», «2» и т. д. Нумерация независима для бюджетов КЦ и ТХ.
- Для новых вспышек бюджет **обязателен** и проверяется сервером. Коды формируются сервером, в транзакции, в виде **«кц1», «кц2» / «тх1», «тх2»**. Изменять код или номер вручную запрещено.
- Архивирование или полностью завершённый выкуп освобождает порядковый номер вспышки. Старая запись получает отдельный архивный код; **все связанные выдачи, остатки, ремонты, брони, пользовательские списки и суммы выкупа остаются у старой записи**. Новая вспышка может занять только освободившийся активный номер.
- Обычная архивация вспышки и выкуп — **разные операции**. Выкупная архивация доступна любому оборудованию лишь при подтверждённой сумме выкупа и **остатке оплаты 0**; обязательно указывается фамилия покупателя. В архиве отображается «Выкуплено · Фамилия»; покупка не выдаётся за возврат в истории. Восстановление проданного оборудования обычной кнопкой запрещено.
- При массовых операциях, копировании и редактировании сервер сохраняет эти правила. Бюджет не угадывать по названию. Исторические вспышки без доказанного бюджета оставлять без перенумерации и выводить в отчёт до ручного выбора бюджета.
- Модели комплектующих и вспышек предлагаются из имеющихся данных, включая архивные; допускается свободный ввод новых моделей. Источник — поля kit_body, kit_lens, kit_flash.
- Любая будущая миграция старых QR-кодов требует отдельной оценки: повторно используемый видимый код после выбытия не должен смешать историю старой и новой вспышки. Перед миграцией обязательна проверенная SQLite-копия и тестирование.

## Поведение склада

- При смене кода товара обновляй ссылки на него в одной транзакции. Проверь остатки, выдачи, историю, брони, паспорт, ремонты, суммы выкупа и пользовательские списки. QR-этикетка содержит код товара, поэтому после смены кода этикетку требуется обновить.
- Полуночные напоминания Основы обслуживает `backend/return_reminders.py`. Граница дня — полночь по Москве. Сотрудник получает напоминание о своей открытой выдаче, а при выдаче гостю его получает выдавший сотрудник. Проверяй доставку на тестовом Telegram-клиенте, включая исключение закрытых выдач и отсутствие повторов после успешной отправки.
- В настройках история оплат показывает учтённые закупки и стоимость завершённых ремонтов. История выкупа строится по записанным событиям. Журнал администратора доступен главному администратору.
- Для отдельной вспышки в комплектации показываются модель и цена вспышки. В сводке «На руках» три столбца — фотоаппараты, вспышки, ноутбуки. Совместимость вспышки определяется по полю модели: C для Canon, S для Sony, ? для неопределённого значения.
- Кнопка сброса фильтров находится под фильтрами на главной и доступна при закрытой панели. Она сбрасывает фильтры, сохраняя поиск и сортировку.
- На Главной «История» остаётся отдельной вторичной строкой под выдачей и QR. Фон спокойнее, чем у основных действий, область нажатия от 44 px. Правило действует в Основе и Бете. Для переходов сохраняй системное уменьшение движения.
- В `backend/index.html` вкладка переключается за 200 мс, основное движение окна занимает 220 мс, закрытие — 150 мс. Подсветка переезжает между вкладками, иконки остаются неподвижны. Действие выполняется сразу, новый переход прерывает предыдущий. Эти параметры одинаковы в Основе и Бете.

## Работа Codex и ChatGPT

- Codex по умолчанию ведёт изменения кода и релиз. ChatGPT ведёт складские задачи, проверяет сценарий и разбирает расхождения. Роли можно передавать. У каждой задачи один текущий исполнитель, у выпуска Основы один ответственный. Перед параллельной работой согласуйте границы изменений и используйте разные ветки.
- Для изменения кода рабочая запись — PR: цель, исполнитель, критерий готовности и подтверждённые проверки. Для складской операции используйте её запись в приложении и приватный рабочий канал. При передаче другому чату передайте ссылку или идентификатор записи, текущего исполнителя и ближайшее действие. При тайм-ауте сначала сверяйте результат операции в приложении, чтобы избежать повторного движения товара.
- Начинайте работу с актуальных `main`, PR и состояния склада, нужных для задачи. После передачи следующий чат сверяет версию и открывает только файлы или записи по задаче. Публичный GitHub подходит для технических данных релиза. Складские данные, резервные копии, учётные данные и приватные обсуждения держите в рабочих источниках с ограниченным доступом.

## Проверка и выпуск

1. Тестируй изменения на отдельной SQLite-базе или копии. Для локального запуска Основы нужна инициализированная база: запуск на отсутствующей базе останавливается специально. Используй отдельные локальные значения конфигурации. Храни токены, сессии, резервные копии и рабочие данные вне Git.
2. Проверяй пользовательский сценарий через обычную точку входа. Для изменений интерфейса используй мобильную ширину браузера. Для операций с данными проверь права доступа и сохранность связанных записей.
3. Перед слиянием дождись зелёной проверки «Склад, выдача и возврат». Публикуй поверх актуального `main` только файлы задачи. При изменении JS или CSS обновляй версию ссылки на затронутый ресурс, чтобы клиенты получили новый файл. Для изменений схемы или миграции данных проверь резервное копирование SQLite перед выпуском.
4. После публикации проверь успешный деплой сервиса Основы в Railway. Убедись, что отвечают `/health` и изменённый маршрут или файл. Для фронтенда проверь новый ресурс и при необходимости вход через `/pwa/`. `/app/version` возвращает отпечаток сборки.
5. В ответе укажи, что проверено локально и на Основе, и какие проверки ещё не подтверждены. Успешный запуск приложения сам по себе не подтверждает доставку сообщения в Telegram.
6. Для передачи после выката возьми `handoff.json` из Actions для нужного SHA. Если ZIP недоступен, тот же JSON есть в аннотации `handoff.json` у проверки `handoff`. Сверь время и поля `checks`. `1` означает, что проверка прошла, `0` означает, что результат не подтверждён. При отсутствии прогона запусти «Сводку релиза Основы» вручную на `main` или выполни `python3 scripts/release_handoff.py` из нужного коммита. Сводка проверяет доступность и отпечаток версии, а сценарий задачи проверяется отдельно.

Если после выпуска обнаружена проблема, ответственный проверяет версию в работе и состояние связанных складских записей. Для отката кода сначала проверь совместимость с текущей схемой. Возврат базы из копии может потерять операции после её создания. Сверь их по журналу до принятия решения.

Для улучшений сравнивай время выполнения повторяющегося сценария до и после изменения. Проверяй, что число дублей, расхождений и неудачных выпусков не растёт. Повторяющийся дефект закрепляй воспроизводимой проверкой.
